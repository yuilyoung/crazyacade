# Pop Pop Arena: 등급 매칭·파티 재경기·운영 동시성

기준은 main `c41ce044`의 고정20개 평가80점이다. 목표85점은 같은 기준으로 독립 평가하며 사전에 배분하지 않는다. 사용자 요청은 동기/비동기·스레드·뮤텍스·세마포어 감사, 실서비스 준비, 재미·등급 매칭·재경기다. 기존 full-auto와 원격 커밋 지시에 따라 구현 선택을 맡아 진행한다. 실제 Supabase/공개 TLS/실사용자 평가 자격 증명은 없고 참가자0명이라는 한계는 유지한다.

## 선택과 검토 근거

Node 단일 경기 루프를 Worker/다중 서버로 전면 교체하는 방법은 아직 부하 근거와 분산 상태 계약이 없다. 기존 구조에서 경기 상태의 동기 소유를 유지하고, 비동기 입장·외부 HTTP·파일·소켓 경계에 제한과 관측을 넣는다. 운영 대상은 Linux Docker 한 인스턴스이며 여러 게임 서버가 하나의 메모리 큐를 공유한다고 주장하지 않는다.

등급 표시만 추가하는 대신 실제 검증한 프로필로 상대를 찾는다. 재미는 새 스킨 수보다 같은 팀으로 세 판을 이어가며 맵과 협동 보너스 목표가 바뀌는 비랭크 파티에서 보완한다. 기존 방·훈련·릴레이·하모니와 기본 선택은 유지한다.

현재 감사에서 인증 HTTP40개 동시 실행, 반복 rematch가 느린 수신자의 bufferedAmount394,632 bytes를 만드는 경로, outbox capacity 검사 전 무제한 Promise 접수 대기, 자체 tmp의 invalid 용량 소모를 재현했다. 단일 JS 이벤트 루프는 await 이후의 논리 경합이나 여러 프로세스의 파일 충돌을 자동 방지하지 않는다.

## 1. 비동기·네트워크 자원 경계

- `createAsyncGate({capacity:4,maxPending:32})`는 FIFO 비동기 세마포어다. `run(task,{signal})`과 `close()/snapshot()`을 제공하고 실행 중4개·대기32개 상한, 대기 취소/오류의 슬롯 반환을 보장한다. main thread를 block하지 않는다. 인증·프로필·레이팅 입장 작업에 공통 적용하며 외부 fetch는 기존5초 timeout을 유지한다.
- 연결 최대256, 전체 방 최대64(기존 연습8·친구AI16 상한도 유지). 매칭 대기열128명. 배포 설정은 정수 유효 범위와 안전 기본값을 검증하며 더 낮은 한도를 테스트할 수 있다. 클라이언트가 한도를 지정할 수 없다.
- 소켓 수신 token bucket 기본 초당30개·burst60개. 초과 입력은 거부하며 지속 남용은1008로 정리한다. 정상 키 반복80ms와 ping/설정/재경기는 영향을 받지 않는다. 같은 준비 상태 요청은 변경·broadcast하지 않는다.
- 송신은64KiB 이상 쌓이면 교체 가능한 state를 생략하고 최신 상태로 회복한다.256KiB 이상 또는3초 이상 지속 지연이면1013으로 정리한다. 일반 제어 응답도 무한 적재하지 않는다. 한 느린 연결 때문에 다른 경기 틱이나 전체 broadcast가 기다리지 않는다.
- `/health`는 생존, `/health/ready`는 신규 경기 수용 여부(정상200/정리 중503), `/health/runtime`은 식별자 없는 수치만 제공한다. 연결/방/큐/인증 active·pending/거부·느린 수신자·tick 처리시간/지연·RSS/uptime의 제한된 허용 목록이다. 계정·JWT·roomId·경기ID·IP·파일 경로·원격 오류 본문은 내보내지 않는다.
- SIGTERM은 drain으로 신규 입장/큐/재경기를 막고 큐 취소를 알린다. 기존 경기는 최대130초 동안 종료할 수 있고, 완료 결과의 durable 접수를 기다린 뒤 종료한다. 강제 종료 제한에 도달한 진행 경기는 정상 완료로 기록하지 않는다. 반복 종료 신호는 안전하게 더 빠른 종료를 요청할 수 있다. 테스트가 종료 시간을 짧게 주입할 수 있어야 한다.

## 2. 결과 Outbox

- 디렉터리 단일 작성자를 Linux `flock`으로 강제한다. 외부 CLI는 고정 인자/명령만 사용하고 사용자 입력을 shell 문자열에 넣지 않는다. 잠금 보유 프로세스는 부모의 pipe가 닫히면 끝나며 OS가 잠금을 해제한다. 파일 존재 여부만으로 lock이라고 판단하거나 살아 있는 작성자의 잠금을 강제로 빼앗지 않는다.
- Docker에 필요한 flock 실행 도구를 명시한다. 개발 게스트 서버는 기존처럼 outbox를 사용하지 않는다. 지원하지 않는 운영 플랫폼/잠금 실패는 시작 실패로 드러난다. 동일 디렉터리의 두 작성자는 동시에 시작하지 못하며 crash 뒤 재시작은 자동 해제된 OS 잠금을 얻는다. 분산 큐 지원은 아니다.
- enqueue의 파일 대기 앞에서 용량을 예약한다. 대기 중인 접수도 capacity에 포함하고 같은 matchId/payload는 한 번만 예약한다. 충돌 payload는 거절한다. 파일 지연/실패에서도 예약이 반환되고 이미 수락한 작업은 종료 때 보존한다.
- `.writer.lock`과 정확히 자체 생성 형식인 임시파일은 유효 결과 용량을 소비하지 않는다. 자체 tmp는 함부로 결과로 승격하지 않고 보존·별도 집계한다. 알 수 없는 파일이나 손상 JSON은 기존 fail-visible 정책을 유지한다. 저장 상태 공개 DTO의 기존 필드는 유지한다.

## 3. 서버 권위 등급 매칭

- 첫 버전은 `team + classic + itemMode:true`의8인 등급 매칭이다. 맵은 서버가5개 중 순환 선택한다. 봇으로 랭크 자리를 채우지 않는다. 친구방·연습·하모니/릴레이는 기존 진입도 유지한다.
- 요청 `queue_join`은 requestId, accessToken, name, characterId, skinId, orbSkinId만 받는다. rating/tier/roomId/teamPreference/humanSlots/practice 등 권한 필드는 거부한다. `queue_cancel {requestId}`은 인증/프로필 조회 중에도 취소된다. requestId는 길이1~64의 제한된 문자열이다.
- 운영에서는 JWT 검증→전역 user claim→프로필 upsert→`readRankedProfile(verifiedUserId)` 순서다. 정확한 한 사용자 rating의 정수/범위를 검증한다. 누락 설정·조회 실패를 개발 모드나 임의1000점으로 대체하지 않는다. 개발 모드는 서버가 생성한 세션과 서버 메모리 레이팅만 쓰고 명시적으로 demo 표시한다.
- 단일 user claim을 입장 작업→큐→배정→매칭방과 복귀 유예까지 보존한다. 매 await 뒤 연결 세대·소켓·claim을 재확인한다. 취소/닫힘/오류는 자신의 세대와 claim만 해제한다. 일반 join으로 큐/매칭방 중복을 우회하지 못한다.
- 매칭 후보는 서버 시간으로 ±100점부터15초마다50점씩 넓혀 최대±400점, 대기 최대180초다. 후보 전체 점수 폭이 모든 참가자의 현재 허용 폭을 만족해야 한다. 오래 기다린 후보를 우선하고 8명을4명씩 나누는35가지 고유 분할에서 양팀 레이팅 합 차이를 최소화한다.
- 배정·큐 제거·방 생성은 await 없는 동기 단위다. 연결이 닫혔거나 방 한도에 도달하면 유효 참가자를 원래 대기 시작시간으로 복구한다. 자동 매칭방은 일반 join을 항상 거부한다.
- 개인 응답 `queue_state`에는 requestId/status(authenticating/searching/cancelled/expired)/source/rating/tier/elapsedMs/searchRadius/requiredPlayers만 둔다. 다른 사용자 목록·ID·토큰은 포함하지 않는다. 성공은 기존 joined→state를 사용하고 `state.matchmaking`으로 출처·고정 정원을 표시한다.
- 완료된 매칭방 `next_match {requestId,matchId}`는 본인만 다시 프로필을 읽고 큐로 이동시킨다. 준비 투표를 먼저 해제하고 비동기 처리 뒤 같은 경기인지 확인한다. 조회 실패는 기존 결과방을 보존하고 재시도할 수 있다. 저장 중인 이전 결과는 독립적으로 계속 전송하며 최신 저장 레이팅만 사용한다.
- 매칭방 재경기는 원래8명이 전부 연결되고 전원 준비한 경우에만 같은 팀으로 시작한다. 탈퇴자가 생긴7인방이 waiting으로 바뀌어 일반 입장으로 채워지면 안 된다. 오래된 matchId 요청은 거부한다.

## 4. 재경기와3라운드 파티

- 기존 rematch는 `ready:true|false`를 지원하고 생략은 true로 유지한다. 준비 취소·상대 이탈·복귀 대기를 UI에서 구분한다. 중복 요청은 멱등이며 새 broadcast를 만들지 않는다.
- `seriesMode:'party3'`는 team 전용, 훈련과 동시 사용 불가, 일반 친구방과 개인 AI 연습에 선택 가능하다. 기본값 single. 파티는 항상 비랭크이며 Outbox와 demo 랭킹에서도 제외한다.
- 한 파티는 정확히3라운드, 각 라운드는 기존120초/승리 조건을 사용한다. 맵 순서는 선택 맵 뒤 harbor/festival/garden에서 중복 없이3개다. 각 판의 승리2점·무승부1점에 팀 협동 목표 달성1점을 더해 마지막 누적 점수로 파티 승패를 정한다. 동점은 파티 무승부다.
- 라운드별 협동 목표는1판 팀 구출2회,2판 팀 아이템5개(아이템OFF면 구출2회),3판 relay/harmony에서 팀 패스3회(classic은 구출2회)다. 실제 room roster의 현재 경기 카운터만 집계하고 목표 보너스는 팀당 라운드당 최대1점이다. 클라이언트가 진척·점수·완료를 지정하지 못한다.
- state.series는 id/round/total/mapCycle/points/mission(종류·목표·양팀 진행)/history/complete/outcome을 허용 목록으로 제공한다. 경기를 끝낼 때 matchId로 한 번만 기록한다. 다음 라운드는 같은 참가자의 준비 합의 뒤 맵/상태를 초기화하고,3라운드 뒤 새 파티도 명시적 준비로 시작한다. 개인 AI 파티는 본인 준비 한 번으로 다음 판을 시작한다.
- 등급 매칭과 파티를 혼합하지 않는다. 초대 URL은 파티 선택을 안전하게 왕복하며 자동 매칭방 초대는 제공하지 않는다. 결과 공유 카드는 실제 본인 경기 수치만 유지한다.

## 5. 화면·검증·평가

- 로비에 등급전 상대 찾기와 파티 선택을 분명히 제공한다. 등급·대기시간·현재 검색 범위·취소·명시적 AI 연습 이동을 표시하며 AI로 몰래 바꾸지 않는다. 결과는 같은 참가자와 재경기/준비 취소/다음 상대 찾기를 구분한다.
- 파티 HUD는 라운드·맵·누적 점수·현재 협동 목표를 짧게 보여 주고 완료 화면에는3판 기록과 실제 기여를 제공한다. 기존 모바일7조작44px·130% 글자·가로 화면·모션/음향 설정을 유지한다.
- 큐·파티·운영 오류를 DOM 없는 ViewModel로 투영하고 오래된 응답/닫힌 화면의 명령을 차단한다. 기술적인 gate/lock/HTTP 내부 사유 대신 플레이어에게 대기·재시도·점검 상태를 안내한다.
- 실제 WS에서 동시 인증/중복 사용자/취소·배정/next_match·rematch/정원/버퍼·입력 폭주를 검사한다. 실제 두 프로세스에서 outbox 잠금·crash·예약·복구를 검증한다. Chromium은 등급 매칭 시작/취소/8인 배정/재경기/다음 상대와3라운드/실제 협동 목표를 검증한다.
- 부하 검사는 localhost 실제 프로세스에서64클라이언트8개 방을60초, 각 클라이언트 정상입력 초당5개와 ping으로 측정한다. p50/p95/p99 RTT, tick 처리/지연, RSS, 정리 후 자원 수와 느린 연결/폭주 한 개의 영향, 제한 초과 거절을 JSON으로 남긴다. 측정 환경과 수치 자체를 공개하며 인터넷 지연·운영 수용량·다중 인스턴스 보장으로 확대하지 않는다.
- 기존307개와11개 브라우저 회귀의 관련 경로, DB/브리지/컨테이너를 확인한다. 독립 코드 리뷰와 같은20개 루브릭으로 평가하고85 미달이면 실제 공백을 보완한다. 인간 재미·인기/잔존율은 미측정으로 유지한다.
