# 등급 매칭의 점수 변화 일관성

기존 승+25/패-15/무+5는 동률 승률이나 반복 무승부만으로 점수가 상승한다. 서버가 수치를 검증하고 양팀 합을 맞추는 기능과, 그 수치가 상대 강도를 반영하는 기능을 구분한다. 사용자의 등급별 매칭·실서비스 고도화 범위에서 전적 점수를 팀 Elo로 보완한다. 인간 실력/밸런스 실증이나 특정 벤치마크 점수는 약속하지 않는다.

## 계산과 저장

- 초기1000·등급 구간·경기 점수/승무패 기록·기존 계정 레이팅은 유지한다. 기존 사용자를 초기화하지 않는다.
- 결과 적용 직전의 각 팀 평균 레이팅으로 기대 승률을 구하고 K32를 사용한다. blue 기대값은 `1/(1+10^((meanPink-meanBlue)/400))`이며 지수 입력의 점수 차이는[-800,800]으로 제한한다.
- 결과는 승1/무0.5/패0, blue 정수 변화량을 한 번 반올림하고 pink에는 반대 값을 적용한다. 정확히 절반인 값은0에서 멀어지는 방향으로 반올림해 JavaScript와 PostgreSQL을 일치시킨다. 각 참가자 레이팅은0~2147483647로 제한한다. 양팀 레이팅이 같으면 승+16/패-16/무0이다. 양팀 인원이 같고 범위 제한이 적용되지 않을 때 합계 변화는0이다. 기존의 인원이 다른 양팀 기록이나 상·하한 적용에서는 합계가0이 아닐 수 있다.
- 개발 모드와 Supabase가 같은 결과를 계산한다. 기존1대1과4대4의 결과/참가자 계약을 보존한다.
- 기존의 빈 경기·참가자 한 명인1대1·한쪽 팀만 있는 결과는 기록과 전적을 유지하되 비교할 상대가 없으므로 레이팅은 바꾸지 않는다. 새로운 정상 등급 매칭은8명을 확보한 뒤 시작한다.
- Supabase는 새 migration으로 record_match를 교체한다. 관련 프로필 행을 안정된 ID 순서로 잠근 뒤 양팀 평균·변경값을 계산하고 같은 트랜잭션에서 한 번 적용한다. 중복 matchId·권한·결과 검증·롤백 경계는 유지한다.
- 결과 큐/RPC 입력에 클라이언트 레이팅을 추가하지 않는다. 저장 지연으로 여러 결과의 적용 순서가 바뀌면 이후 계산도 영향을 받을 수 있다. 경기 시작 시점 레이팅을 저장한 것처럼 설명하지 않는다.

## 검증과 소유권

match85_impl은 순수 계산/개발 집계, 새 SQL migration·테스트, migration 실행 스크립트를 담당한다. 동등 팀·강약 팀·무승부·하한·큰 점수 차이·탈퇴 포함 최종 roster·중복 결과와 DB 권한/트랜잭션을 검사한다. 기존 SQL을 읽은 뒤 RPC 계약을 유지한다. 실제 Supabase에는 적용하지 않는다.

client85는 고정 가감점 안내가 있다면 상대 강도에 따라 달라짐을 설명한다. 서버가 제공하지 않은 개인 점수 변화량을 만들어 표시하지 않는다. root는 README의 새 migration 순서·프로토콜·서비스 한계를 정리하고 실제 격리 PostgreSQL과 최종 통합/부하/독립 검토를 확인한 뒤 원격 반영한다.
