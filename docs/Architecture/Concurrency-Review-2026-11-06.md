# 동시성·스레드·잠금 검토

검토 대상은 Node 서버와 브라우저 POC이며, 변경 전 기준은 `c41ce044`다. Unity는 소스만 검토했고 C# 컴파일·WebGL 빌드는 실행하지 않았다. 이번 고도화는 공유 경기 상태의 소유권을 유지하면서 외부 I/O의 동시성과 대기량을 제한한다.

## 실행 방식

| 경계 | 실행 및 동기화 방식 | 보장 범위 |
| --- | --- | --- |
| 경기 틱·이동·물폭탄·구출·승패 | Node의 한 이벤트 루프에서 `await` 없는 동기 계산 | 한 프로세스 안에서 경기 상태를 동시에 수정하는 게임 스레드가 없음 |
| 인증·프로필·레이팅 조회 | 비동기 HTTP, 제한시간·AbortSignal, FIFO admission gate | 기본 실행4개·대기32개, 취소된 대기는 즉시 제거. 실행 중 작업은 실제 종료할 때 슬롯 반환 |
| 입장·매칭·복귀 | 세션 작업 세대와 사용자 claim, `await` 뒤 재검사 | 늦게 도착한 인증 결과·취소·다른 소켓의 복귀가 현재 소유권을 덮어쓰지 않도록 검사 |
| 8인 배정·팀 구성 | 순수 후보 선택 뒤 같은 동기 turn에서 방 생성·큐 제거 | 연결·정원·claim을 마지막에 검사하며 중간에 비동기 I/O 없음 |
| 결과 파일 변경 | Promise 체인으로 비동기 mutation 직렬화 | 프로세스 내부 async mutex 역할. OS 스레드를 블로킹하는 Mutex는 아님 |
| 결과 접수·전송 | 디스크 대기 전 용량 예약, 동시 전송2개 | 대기 파일 쓰기도1000개 상한에 포함. 같은 ID/내용은 합치고 충돌 내용은 거절 |
| 결과 디렉터리 | Linux `flock` 배타 잠금 | 같은 로컬 디렉터리의 두 작성자 시작을 거절. 프로세스 강제 종료 후 OS가 잠금 반환 |
| DB 결과 집계 | UUID 순서의 프로필 행 잠금·PostgreSQL 트랜잭션·고유 경기 ID | 겹치는 참가자의 결과 적용을 직렬화하고 같은 결과의 점수·레이팅을 한 번 집계 |
| 브라우저 | 단일 UI 이벤트 루프, WebSocket 이벤트·Promise·작업 세대 | 읽기 전용 ViewModel과 입력/렌더/통신 경계를 사용. 서버 경기 상태를 업로드해 복원하지 않음 |
| Unity 소스 | 코루틴·UnityWebRequest·WebGL JS 콜백 | 명시적 Thread/Task/Mutex/Semaphore 구현은 찾지 못함. 코루틴 자체는 병렬 스레드가 아님 |

게임 상태 계산용 Worker Thread·SharedArrayBuffer·OS 세마포어는 애플리케이션에서 사용하지 않는다. 경기 상태는 Node 주 이벤트 루프가 소유하지만 런타임의 I/O 스레드 풀과 OS의 비동기 I/O 처리는 별도로 존재한다. 인증 gate와 결과 전송 슬롯은 **비동기 세마포어에 해당하는 동시성 제한**이다. CPU 병목 측정 없이 게임 상태를 여러 스레드로 나누면 동기화할 공유 상태가 늘어나므로 이번 변경에는 게임 계산 Worker를 추가하지 않았다.

## 레이팅 결과 적용의 원자성

`20261106_team_elo.sql`은 앞선 경기 기록·랭킹 마이그레이션 뒤 적용하며 기존 레이팅과 기록을 보존한다. `record_match`는 관련 프로필을 UUID 순서로 `FOR UPDATE` 잠근 뒤 결과 적용 직전의 최신 저장 레이팅으로 양팀 평균을 구한다. 이 잠금을 경기/참가자 외래 키 삽입보다 먼저 취득하여 겹치는 명단이 키 공유 잠금에서 갱신 잠금으로 바꾸며 서로 기다리는 경로를 피한다. 평균 산출·참가자 기록·레이팅과 통계 변경은 같은 트랜잭션이며 실패 시 함께 롤백한다. 기다리는 사이 같은 `matchId`가 기록된 경우에도 고유 키와 삽입 결과 검사로 중복 갱신을 막는다.

K32 팀 Elo는 평균 차이를±800으로 제한하고 한쪽 변화량만 부호를 보존해 반올림한 뒤 다른 쪽에는 반대 값을 적용한다. SQL의 numeric 반올림과 JavaScript의 절댓값 반올림은 정확히 절반이면0에서 멀어지는 규칙을 공유한다. 최종 레이팅은0~2,147,483,647이며 SQL은 bigint 덧셈 후 제한하고 JavaScript는 덧셈 전에 범위를 검사한다. 개발 집계도 모든 참가자의 변경 전 메모리 값을 먼저 복사한 뒤 한 번에 변화량을 계산한다. 상대 참가자가 없는 과거 호환 결과는 레이팅을 바꾸지 않고 존재하는 참가자의 통계만 기록한다.

결과 전송2건이 동시에 진행돼도 겹치는 프로필은 DB 행 잠금으로 순서가 정해진다. 다만 그 순서가 경기 시작·종료 순서를 보장하지는 않는다. Outbox 지연·재시도로 적용 순서가 달라지면 뒤의 Elo 계산도 영향을 받는다. 큐/RPC에 경기 시작 레이팅이나 클라이언트가 지정한 레이팅을 추가하지 않았으며, 디렉터리 잠금과 DB 행 잠금의 역할은 별개다. 실제 Supabase 프로젝트 적용·공개 운영과 인간 실력에 대한 검증은 여전히 별도다.

## 변경 전 재현한 문제와 보강

1. 응답이 지연된 인증 서비스에40개 연결을 보내면40개 외부 요청이 동시에 실행됐다. 이제 인증·프로필 조회를 gate 안에서 처리하고 접속 수·방 수·큐 인원도 제한한다.
2. 결과 큐 용량이1개여도 첫 파일 쓰기가 막히면100개 추가 enqueue가 Promise 체인에 대기했다. 이제 접수 시점에 예약하며 초과 요청을 디스크 작업 전에 거절한다.
3. 읽기를 멈춘 소켓에 중복 준비 요청을 보내면 송신 대기가394,632바이트까지 증가했다. 이제 같은 준비 상태는 재방송하지 않고 소켓별 수신 비율·송신 대기를 제한한다.
4. 자체 임시 파일 하나가 손상 파일로 집계되어 용량1개 큐를 막았다. 정확히 자체 UUID 임시 파일 형식인 경우 원본 바이트를 보존하고 별도 진단한다. 알 수 없는 파일을 임의 삭제하지 않는다.
5. 디렉터리 단일 작성자는 문서상의 조건이었다. 이제 영구 `.writer.lock` inode를 `flock -n -o`로 잠가 두 번째 프로세스를 시작 단계에서 거절한다.

## 잠금과 종료의 구체적 한계

결과 디렉터리의 `.writer.lock`은 삭제하지 않는다. 살아 있는 프로세스의 lock 파일을 지우면 서로 다른 inode에 잠금을 잡을 수 있기 때문이다. 잠금 자식은 고정된 shell 프로그램을 실행하며 사용자 문자열을 shell 명령으로 조립하지 않는다. 부모 stdin pipe의 수명으로 잠금을 유지하고 `-o`로 명령 자식의 lock descriptor 상속을 막는다. 부모 SIGKILL·취득 제한시간·정지한 lock 프로세스의 종료를 실제 자식 프로세스로 검사한다.

이는 Linux 로컬 파일시스템의 단일 서버를 위한 보호다. NFS·다중 서버 분산 큐·분산 락을 검증한 것은 아니다. 경기·매칭 큐·복귀 토큰은 메모리에 있고 서버 재시작 후 복원하지 않는다.

SIGTERM은 신규 입장·매칭·재경기를 중단하고 readiness를503으로 바꾼다. 진행 중 경기는 최대130초 동안 종료를 기다리며, 기한에 남은 경기를 완료 결과로 꾸미지 않는다. 이미 접수한 결과 파일 쓰기는 끝까지 기다린다. **130초는 경기 drain 기한이며, 멈춘 파일시스템의 종료 상한을 보장하지 않는다.** 운영의 종료 유예는 경기 drain에 저장 시간을 더해 설정해야 한다. 강제 종료 뒤에는 디스크에 기록된 완료 결과만 복구한다.

## 검증 자료

`async-gate.test.js`, `runtime*.test.js`는 FIFO·취소·실패 슬롯 반환·실제 폭주 소켓·읽기 중단 소켓·정상 연결 진행을 검사한다. `directory-lease.test.js`, `outbox-concurrency.test.js`, 기존 결과 저장 통합 검사는 지연 파일시스템·용량·중복·두 프로세스·SIGKILL 복구를 검사한다. 매칭/파티 테스트는 실제 WebSocket과 로컬 인증 fixture를 사용한다.

부하 수치는 [서비스 준비 상태](../Operations/Service-Readiness.md)와 최종 벤치마크에 별도로 기록한다. 로컬 동시 연결 수를 공개 인터넷 서비스의 수용량으로 환산하지 않는다. 기존 [OOP·MVVM 검토](OOP-MVVM-Review-2026-11-06.md)의 공유 Room 상태와 Unity UI 결합은 여전히 후속 과제다.
