# 서비스 준비 상태 (2026-11-03)

브라우저4대4 전투·아이템·점수·랭킹, AI 연습·훈련·친구 초대·재대결·연결 복구와 결과 저장 큐를 구현했다. 최신 증분은 외형·두 새 맵과 수문·하모니 패스/구출 충전·실조작 훈련·화면/조작/음향 설정·개인 결과 공유와 VM/규칙 경계 분리다. 최종 검증 기록은 [POC 완료 기준](../Design/POC-Acceptance.md)과 [벤치마크06](../Design/Benchmark-06-Experience.md)을 따른다. 설계 평가80점은 공개 서비스 준비율80%가 아니다. 실제 Supabase·공개 배포·운영 부하·Unity C# 빌드·인간 플레이 테스트는 미검증이다.

현재 서버는 한 프로세스 메모리에 룸과 복귀 권한을 보관한다. 브라우저 재접속은 같은 프로세스에서 30초 유예 안에 돌아오는 경우를 대상으로 한다. 자동 매칭, 다중 서버 룸 라우팅, 프로세스 재시작 후 진행 경기 복원은 없다. 완료 결과는 별도 파일 큐로 복구하며 점수판의 saved는 실제 DB 성공 응답을 받은 경우에만 표시한다.

운영 클래식 결과 큐의 경로는 `RESULT_OUTBOX_DIR`이며 기본값은 실행 디렉터리의 `data/results`다. Docker의 `/app/data/results`를 유지하려면 `/app/data`에 영속 볼륨을 연결한다. 새 디렉터리/파일은700/600 권한으로 만들고 원자적 파일 교체를 사용한다. 같은 경로는 한 프로세스만 사용한다. 컨테이너 교체 때 디스크를 버리면 미전송 파일도 복구할 수 없다. 진행 중 경기·로그인·복귀 토큰은 이 큐에 저장하지 않는다.

큐는 최대1000개·레코드당32KiB이며 동시에2건을 전송한다. 파일 기록 완료 후 HTTP를 호출하고5초 안에 응답하지 않으면 제한 시간을 적용한다. 네트워크·timeout·408/429/5xx에는1/2/5/10/30초 이후30초 간격으로 재시도한다. 기타4xx·누락 설정으로 failed가 된 보관 파일은 원인 수정 후 같은 경로로 서버를 재시작하면 다시 처리한다. 동일 matchId를 재사용하므로 DB commit 뒤 응답이 유실되어도 점수·레이팅을 중복 반영하지 않는다. 큐 포화/파일 쓰기 실패는 실패로 알리며 접수하지 못한 결과의 디스크 보존을 약속하지 않는다.

`/health`는 liveness이고 `/health/storage`는 큐 상태 집계다. `status=degraded`는 HTTP503으로 보고한다. failed/invalid 증가를 운영에서 관측하고 디스크·설정·DB 오류를 확인해야 한다. 손상·지원하지 않는 파일은 자동 삭제하지 않으며 invalid로 집계한다. 파일 경로·계정·경기ID·토큰·오류 응답 본문을 공개하지 않는다. 개발 모드 disabled, 연습·릴레이 unranked는 영구 저장 완료와 별개다. 운영 모니터·알림·백업의 실제 연결은 아직 검증하지 않았다.

검증 명령과 범위는 [POC 완료 기준](../Design/POC-Acceptance.md), 활성화 설정은 [GitHub 자동화 안내](GitHub-Automation.md), Supabase 설정은 [README](../../README.md)를 따른다. 실제 Supabase, 원격 Actions, GHCR 게시, 공개 배포 성공을 로컬 검증으로 대신하지 않는다.

비랭크 연습은 계정 없이 허용하는 별도 경로이며 사람 대전 인증 우회 기능이 아니다. 운영 환경에도 프로세스당 연습방 8개 제한과 연결 정리가 적용된다. 복귀 유예 중인 연습방도 정원에 포함되고 명시적 이탈이나 유예 만료 때 정리된다. 공개 대규모 트래픽을 위한 요청/연결 비율 제한 및 관측은 별도 운영 과제다.

팝 릴레이는 인증된 사람 대전도 비랭크이며 기존 클래식 레이팅과 분리된다. 연결이 끊긴 운반자는 별을 떨어뜨리고 복귀 대기 중 다시 획득하지 않는다. 경기는 계속되며 연결 복구가 피격·탈락을 취소하거나 추가 무적을 주지 않는다. 같은 방 재대결은 별도 기능이며 복귀 유예 중인 참가자도 기다린다.

복귀 토큰은 참가자에게만 보내고 브라우저의 탭별 `sessionStorage`에 보관한다. 초대 링크·공개 state·로그에 포함하지 않는다. 인증 입장자는 복귀 때 유효한 JWT와 동일 사용자 검증이 필요하다. 토큰을 가진 새 연결이 복귀하면 이전 소켓을 교체하며 이전 연결은 입력을 보낼 수 없다. Unity와 opt-in하지 않은 구형 클라이언트는 기존 즉시 이탈 동작을 유지한다. 이 경계는 로컬 인증 fixture 검사 대상이며 실제 Supabase 검증을 대신하지 않는다.
