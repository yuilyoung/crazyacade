# 서비스 준비 상태 (2026-11-06)

브라우저4대4 전투·아이템·점수·랭킹, AI 연습·훈련·친구 초대·재대결·연결 복구와 결과 저장 큐를 구현했다. 최신 증분은 서버 레이팅 기반8인 매칭·팀 Elo,3라운드 협동 목표·누적 개인 기록, 훈련 읽기 시간 보존, 모바일 목표/조작 배치와 운영 동시성 보호다. 최종 검증 기록은 [POC 완료 기준](../Design/POC-Acceptance.md)과 [벤치마크07](../Design/Benchmark-07-Matchmaking-Party.md)을 따른다. 설계 평가 점수는 공개 서비스 준비율이 아니다. 실제 Supabase·공개 배포·인터넷/장시간 운영 부하·Unity C# 빌드·인간 플레이 테스트는 미검증이다. 로컬 부하와 운영 보호의 이번 검증은 아래 증분을 따른다.

현재 서버는 한 프로세스 메모리에 룸과 복귀 권한을 보관한다. 브라우저 재접속은 같은 프로세스에서 30초 유예 안에 돌아오는 경우를 대상으로 한다. 서버 권위 레이팅 기반8인 자동 매칭은 같은 프로세스 안에서 제공한다. 다중 서버 룸 라우팅, 프로세스 재시작 후 진행 경기 복원은 없다. 완료 결과는 별도 파일 큐로 복구하며 점수판의 saved는 실제 DB 성공 응답을 받은 경우에만 표시한다.

운영 클래식 결과 큐의 경로는 `RESULT_OUTBOX_DIR`이며 기본값은 실행 디렉터리의 `data/results`다. Docker의 `/app/data/results`를 유지하려면 `/app/data`에 영속 볼륨을 연결한다. 새 디렉터리/파일은700/600 권한으로 만들고 원자적 파일 교체를 사용한다. 같은 경로는 한 프로세스만 사용한다. 컨테이너 교체 때 디스크를 버리면 미전송 파일도 복구할 수 없다. 진행 중 경기·로그인·복귀 토큰은 이 큐에 저장하지 않는다.

큐는 최대1000개·레코드당32KiB이며 동시에2건을 전송한다. 파일 기록 완료 후 HTTP를 호출하고5초 안에 응답하지 않으면 제한 시간을 적용한다. 네트워크·timeout·408/429/5xx에는1/2/5/10/30초 이후30초 간격으로 재시도한다. 기타4xx·누락 설정으로 failed가 된 보관 파일은 원인 수정 후 같은 경로로 서버를 재시작하면 다시 처리한다. 동일 matchId를 재사용하므로 DB commit 뒤 응답이 유실되어도 점수·레이팅을 중복 반영하지 않는다. 큐 포화/파일 쓰기 실패는 실패로 알리며 접수하지 못한 결과의 디스크 보존을 약속하지 않는다.

`/health`는 liveness이고 `/health/storage`는 큐 상태 집계다. `status=degraded`는 HTTP503으로 보고한다. failed/invalid 증가를 운영에서 관측하고 디스크·설정·DB 오류를 확인해야 한다. 손상·지원하지 않는 파일은 자동 삭제하지 않으며 invalid로 집계한다. 파일 경로·계정·경기ID·토큰·오류 응답 본문을 공개하지 않는다. 개발 모드 disabled, 연습·릴레이 unranked는 영구 저장 완료와 별개다. 운영 모니터·알림·백업의 실제 연결은 아직 검증하지 않았다.

검증 명령과 범위는 [POC 완료 기준](../Design/POC-Acceptance.md), 활성화 설정은 [GitHub 자동화 안내](GitHub-Automation.md), Supabase 설정은 [README](../../README.md)를 따른다. 실제 Supabase, 원격 Actions, GHCR 게시, 공개 배포 성공을 로컬 검증으로 대신하지 않는다.

브라우저 전투 모션 증분은 서버 프로토콜·판정·저장소를 변경하지 않는다. 최종 컨테이너의 서버/공개 파일57개가 검증 소스와 일치하며 비루트·운영 게스트 거부·공유 볼륨 작성자 잠금·재시작 검사를 통과했다. 별도의 한 화면 렌더 표본은 녹화 중179개 rAF 간격, 중앙값33.3ms·p95 33.4ms·최대150ms였다.8개 페이지·녹화1개 조건의 중앙값은 풍성한 효과100ms, 최소 효과83.3ms로 달랐다. 공유 호스트의 짧은 자동 브라우저 표본이며, 이전64연결 서버 부하 검사를 브라우저60fps나 실기기 성능의 근거로 사용하지 않는다.

비랭크 연습은 계정 없이 허용하는 별도 경로이며 사람 대전 인증 우회 기능이 아니다. 운영 환경에도 프로세스당 연습방 8개 제한과 연결 정리가 적용된다. 복귀 유예 중인 연습방도 정원에 포함되고 명시적 이탈이나 유예 만료 때 정리된다. 프로세스별 접속/메시지 비율 제한과 숫자 집계가 있으며, 공개 대규모 트래픽의 엣지 보호·분산 제한·운영 알림은 별도 과제다.

팝 릴레이는 인증된 사람 대전도 비랭크이며 기존 클래식 레이팅과 분리된다. 연결이 끊긴 운반자는 별을 떨어뜨리고 복귀 대기 중 다시 획득하지 않는다. 경기는 계속되며 연결 복구가 피격·탈락을 취소하거나 추가 무적을 주지 않는다. 같은 방 재대결은 별도 기능이며 복귀 유예 중인 참가자도 기다린다.

복귀 토큰은 참가자에게만 보내고 브라우저의 탭별 `sessionStorage`에 보관한다. 초대 링크·공개 state·로그에 포함하지 않는다. 인증 입장자는 복귀 때 유효한 JWT와 동일 사용자 검증이 필요하다. 토큰을 가진 새 연결이 복귀하면 이전 소켓을 교체하며 이전 연결은 입력을 보낼 수 없다. Unity와 opt-in하지 않은 구형 클라이언트는 기존 즉시 이탈 동작을 유지한다. 이 경계는 로컬 인증 fixture 검사 대상이며 실제 Supabase 검증을 대신하지 않는다.

## 매칭·파티·동시성 증분

등급 매칭은8인 클래식 아이템전 하나의 풀이다. 운영에서는 JWT의 사용자 ID로 프로필을 생성/확인하고 서버 전용 키로 해당 사용자의 저장 레이팅을 조회한다. 공개 상위50명 랭킹이나 클라이언트 점수를 매칭 값으로 사용하지 않는다. 검색 중인 사용자는 일반방·다른 큐에 중복 입장할 수 없고, 매칭방의 복귀 유예 중에도 계정 claim을 유지한다. 같은 상대 재경기는 원래8명이 필요하고 다음 상대 찾기는 프로필 재조회가 성공한 뒤 이전 결과방을 떠난다. 큐와 레이팅 창은 한 서버 안에서만 공유된다.

레이팅 갱신은 K32 팀 Elo이며 결과를 적용하기 직전의 최신 저장 레이팅으로 양팀 평균을 구한다. 기존 계정 값은 초기화하지 않고 신규 계정은1,000에서 시작한다. 동등 평균은 승+16/패−16/무0이며 상대 강도에 따라 달라진다. 평균 차이는±800, 최종 개인 값은0~2,147,483,647로 제한한다. 개발 메모리 집계와 SQL은 같은 부호별 반올림·상대 팀 반대 변화량을 사용하며, 상대 참가자가 없는 과거 호환 기록은 레이팅 변화 없이 존재하는 참가자의 통계만 반영한다. 구체적인 식과 검증 계약은 [프로토콜](../Architecture/Realtime-Protocol.md#랭킹-http-api)을 따른다.

운영 SQL은 참가자 프로필을 UUID 순서로 잠근 뒤 평균과 결과를 같은 트랜잭션에서 적용한다. Outbox의 지연·재시도는 결과 적용 순서와 이후 Elo 변화량에 영향을 줄 수 있다. 경기 시작 당시 레이팅을 고정한 계산이 아니며 결과가 아직 저장 중일 때 다음 상대 검색은 마지막 저장 값을 사용한다. 이 수치의 일관성을 인간 실력 추정이나 실제 매칭 밸런스 검증으로 확대하지 않는다.

3라운드 파티는 친구방/개인 AI 연습용 비랭크다. 매판 다른 맵, 승2/무1/협동 목표1점, 실제 구출·아이템·패스 카운터, 마지막 종합 승패를 사용한다. 봇·파티·훈련·릴레이·하모니를 랭크 집계에 넣지 않는다. 사람의 재미·재경기 의향·밸런스는 자동 브라우저 성공으로 입증하지 않는다.

| 기본 상한 | 값 | 초과 시 동작 |
| --- | ---: | --- |
| WebSocket 연결 | 256 | 새 연결 거절 |
| 전체 방 / 매칭 대기 | 64 / 128 | 새 방·큐 접수 거절 또는 기존 큐 대기 유지 |
| 인증 실행 / 대기 | 4 / 32 | FIFO 대기, 대기 초과 거절, 취소한 작업 정리 |
| 소켓 입력 | 초당30 · 순간60 | 초과 입력 무시, 지속 위반 연결 종료 |
| 송신 대기 | 64KiB / 256KiB | 최신 상태 생략 / 연결 종료. 지연3초도 종료 |
| 경기 drain | 130초 | readiness503·신규 작업 중단·남은 미완료 경기 연결 정리 |

상한은 `Server/.env.example`의 `RUNTIME_*` 변수로 제한된 범위에서 조정한다. 틱은100ms이며 게임 상태는 Node 주 이벤트 루프가 소유하고, 런타임·OS의 I/O 처리는 별도로 진행된다. 자세한 동기/비동기·세마포어·잠금과 재현은 [동시성 검토](../Architecture/Concurrency-Review-2026-11-06.md)를 따른다.

### 배포·종료 점검

- Supabase는 `schema.sql` 뒤 `20261102_team_match_history.sql` → `20261102_rankings.sql` → `20261106_team_elo.sql` 순서로 적용한 뒤 새 서버를 배포한다. 세 번째 마이그레이션은 기존 계정/기록을 유지하며 `record_match` 집계 함수를 교체한다. 실제 프로젝트 적용과 운영 키 설정은 로컬 검증에 포함되지 않는다.
- 제공 Docker는 Node24 Debian slim과 기본 util-linux `flock`을 사용하며 UID1000으로 실행한다. 영구 결과 큐를 사용하는 직접 실행도 Linux `flock -n -o --`가 필요하다.
- 준비 검사에는 `/health/ready`, 생존 검사에는 `/health`를 사용한다. `/health/runtime`은 연결·방·큐·인증 대기·틱 지연·RSS·제한 발생 횟수만 제공하며 계정/방 ID·토큰을 공개하지 않는다. 이 숫자를 수집하는 운영 모니터/알림 연결은 별도다.
- SIGTERM 후 기존 경기 입력은 계속 처리한다. 새 소켓을 받지 않으므로 종료 기간의 끊어진 연결 복귀는 보장하지 않는다. 이미 열린 소켓의 유효 복귀는 처리한다.
- 오케스트레이터의 종료 유예를 설정된 `RUNTIME_DRAIN_MS`보다 길게 두고 파일 저장 시간도 확보한다. 기본 경기 대기는130초이고 Render 연습 데모는20초로 줄인다. 파일시스템이 멈추면 accepted write drain에 유한 종료 보장이 없으며, 강제 종료는 아직 디스크에 기록하지 못한 결과를 잃을 수 있다.
- `.writer.lock`은 정상적으로 남긴다. 시작 시 잠금 충돌이면 기존 서버를 정상 종료하고 다시 시작한다. 살아 있는 작성자의 lock 파일을 지우지 않는다. 자체 UUID 임시 파일은 복구 가능한 완료 결과로 승격하지 않고 보존하며, 남아 있으면 storage 상태가 degraded다. 운영자가 백업 후 경로를 조사한다.

### 재현 명령과 해석

`npm test`(Server), `python3 scripts/matchmaking85-smoke.py`, `python3 scripts/party85-smoke.py`, `node scripts/load85-smoke.mjs`를 저장소 루트 기준으로 실행한다(첫 명령만 Server 디렉터리). 부하 스크립트는 별도 로컬 서버에64개 실제 WebSocket/8개 방을60초 연결하고 입력·왕복 지연·틱·RSS·정리를 측정한다. 결과는 `docs/Design/evidence/benchmark85-load.json`에 기록한다. 인증 fixture와 로컬 PostgreSQL은 실제 Supabase 프로젝트가 아니다. CPU·프로세스 경합·네트워크 조건에 따라 측정값이 달라지므로 운영 최대 인원으로 광고하지 않는다.

2026-11-06 실제 실행은 입력19,200회·ping3,840회를 처리했고 입력 배치 누락은0이었다.
